# 设置页信息架构：交接 brief

> 用途：模型/会话切换时的上下文交接。只记录**现状、待决策、备选方案**，不含实现代码。
> 稳定后应并入 `DEVELOPMENT.md` 的「ClickGUI / 设置系统速查」一节。

## 一、目标

优化"模块设置页"的信息架构与 UX：先定**设计语言**（什么该是节、什么该是组、开关落在哪一层），
再逐模块迁移。判据是"打开设置页能否一眼看出：哪些是独立小功能、哪些只是参数分组"。

## 二、现状事实（代码层，已核对）

1. 设置系统里有两个容器类型，**语义与外观错位**：
   - `Setting.Header(label[, subtitle])`：纯文本标题，无开关、不可交互，用于分隔
     （`gui/setting/Setting.java` 第 745 行起）。
   - `Setting.GroupSetting(label, children[, toggle])`：可折叠，**可以带总开关**
     （同文件第 527 行起）。
2. 因此"这一行能不能点"取决于作者当时选了哪个类型，而不是语义 —— 这就是设计语言混乱的根源。
   典型：`ModuleDefinitions.java` 里后处理/准星用**带开关的组**表示小功能，
   玩家数值显示页用**不带开关的 Header** 做分组标题。
3. 具体反例（已修一半）：`damage_splash` 模块曾把"模块开关"直接当作 `Compact` 的开关，
   导致 `Uppercase formatting` 没有独立位置。

## 三、已完成的局部改动（本方向的第一步）

`伤害飘字` 模块现在拆成**两层开关**：

| 层 | 字段 | 含义 |
|---|---|---|
| 模块总开关 | `damageSplashEnabled` | 关 = 整个功能不接管、不渲染（回原版） |
| 合并 | `damageSplashCompactEnabled` | 关 = 不合并，每个飘字独立显示，但仍自绘并格式化 |
| 大写格式化 | `damageSplashUppercase` | 关 = `1,234,567`；开 = `1.23M` |

即：**模块开关 ≠ 小功能开关**，这是后续所有模块要遵循的方向。

## 四、待确认的模型（上一轮讨论停在这里）

三层：**模块 → 节 → 组**

- **模块**：一个功能领域，卡片上一个总开关。
- **节**：一个**可独立开关的小功能**，节头自带开关；页面上的设置都必须归属于某个节。
- **组**：节内部**同类设置的归类**，**不带开关**，可折叠。

判断口诀：**能单独关掉、玩家会单独关掉的东西 = 节；只是把参数分堆看 = 组。**

推论：节必须有开关（哪怕只有一个设置，那就是它自己）；组永远不带开关；一个设置只属于一个节。

例外（待确认）：**"共享设置节"** —— 无开关、纯排版，用于跨多个小功能共享的设置（如"颜色"）。

## 五、备选方案

| 方案 | 做法 | 评价 |
|---|---|---|
| **A** 保留两类型，只强化视觉差异 | 节无背景/无箭头，组卡片化 + chevron | 最小改动，但语义错位仍在 |
| **B（推荐）** 合并为 `Section` 类型 | 标题 + 副标题 + 可选开关 + 子项；`GroupSetting` 退化为无开关的折叠容器 | 外观由语义唯一决定，需要改 `Setting`、`SettingsView`、`HudSettingsCard` 三处 |
| **C** 只留节 | 去掉组 | 会丢失"整块折叠 / 一键关"的能力 |

配套硬规则：**一个页面最多一层组；组内不再出现节。** 需要"组里再分块"时，说明该拆成两个节。

## 六、伤害飘字页的目标结构

```
模块「伤害飘字」                  [总开关]
├─ 节「大写格式化」               [开关]      ← 唯一设置就是它自己
└─ 节「合并」                     [开关]
     归属半径 / 合并窗口(毫秒) / 显示次数
     显示时长(毫秒) / 淡出(毫秒) / 右侧偏移 / 行高
```

7 个参数暂不套组（建议阈值：单节 > 6 项才分组，可分为「合并规则」「显示」两个组）。
